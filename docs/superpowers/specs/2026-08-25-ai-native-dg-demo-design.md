## 一、背景与目标

- 起点：AI 数据治理三层架构图（Copilot 层 / Agent 层 / Skill 层）
- 对标：**SAP MDG**（中央治理、Consolidation、DQM、Key Mapping、Replication）
- 竞争坐标：
  - **用友** = 传统规则型完整方案（功能全，AI 是外挂）
  - **中翰软件 × 魏桥创业集团** = AI-native MDM 已落地标杆（Navigate OS，[2026-08 报道](https://m.sohu.com/a/1062315598_122873738)；功能描述仅厂商单方来源，效果数字无第三方验证）
- **定位（v3 定稿）**：**AI 增强型确定性治理平台**。核心治理逻辑（标准校验、质量规则、归并执行、编码映射）由确定性规则引擎承载——主数据零容错场景下这是唯一正确的工程判断；LLM 在建议层增强语义判断、候选召回、冲突提示、证据组织与自然语言交互。
- **不回避的问题（回应批评1）**：这个定位下 LLM 抽掉系统仍能跑，我们**不假装这是 AI-native**。demo 的代差优势不在"自动化"，而在**治理体验三层代差**：
  1. **决策速度**：责任人从"3 天翻表查证"到"30 分钟带着证据裁决"
  2. **决策质量**：证据链让漏判、错判、拍脑袋减少——AI 帮人看见看不见的风险
  3. **决策透明**：每个决定可追溯、可复盘、可归因——这是传统 MDM 给不了的
  - AI 增强的不可替代点（抽掉 LLM 就消失的能力）：规则查不到的同义变体候选召回、跨标准差异的主动冲突提示、自然语言交互降低使用门槛。**演示卖点 = 治理体验，不是治理自动化**。
- **AI 的真实价值主张**：**AI 提升人的判断效率，不替代人的治理责任**。AI 也会错，系统的价值在于让 AI 的错误**可见、可拦、可追**。
- 本次目标：demo showcase 完成技术论证——证明"确定性治理 + AI 建议增强"路线可行，且在核心环节有可演示的代差优势。
- 用途：双目标，先内后外——对内立项论证（拿预算），对外售前 POC。
- 载体：扩展现有 RalphLoop 平台（演示完即产品雏形）。

## 三、制造业数据治理全景图

### 3.1 系统能力活动（数据生命周期，对标 MDG 能力域）

1. **数据盘点**：存量摸底、质量基线
2. **标准管理**：分类/属性/编码/命名四类标准的定义、发布、版本 ⭐ demo 聚焦
3. **质量治理**：规则定义→检核→工单→整改→报告（对标 DQM） ⭐ demo 聚焦
4. **归并与清洗**：重复识别、匹配合并、最佳记录、一物多码映射（对标 Consolidation + Key Mapping） ⭐ demo 聚焦
5. **变更管控**：增/改/冻结/归档全走工作流（对标 Change Request）
6. **分发与共享**：金标分发消费系统、编码映射同步（对标 Replication）
7. **安全与合规**：分级、敏感属性管控、审计
8. **运营度量**：质量 KPI、流程时效、重复率趋势

> 注：SAP MDG 产品只覆盖 4-7，1-3、8 靠平台扩展或实施补齐——"买了 MDG ≠ 治理成功"。

### 3.2 治理权责模型（最小闭环，权责冲突进故事线）

| 角色 | 职责 | demo 落点 |
|------|------|-----------|
| 业务 Owner（物料域） | 归并与标准争议的最终裁决 | 裁决卡片显示 Owner 姓名/部门；改判留痕 |
| 数据管家（Steward） | 质量工单整改、建议初筛 | 工单指派到人；整改闭环可查 |
| 审批链 | 变更/归并/标准发布的逐级审批 | 复用审批流骨架，展示审批链与**升级路径** |
| 问责链 | AI 建议 + 人工批准的全程留痕 | `agent_trace` + 审批记录 + 证据快照 + 模型版本，回答"错了谁负责、当时依据什么批的" |

**权责冲突场景（v3 新增，进 demo 脚本）**：
- **跨事业部归并争议**：归并建议涉及工厂 A（同意）与工厂 B（反对，旧码失效影响其生产）→ 争议工单升级审批链 → 双方 Owner 会签 → 决策留痕
- **标准过时**：Agent 校验"命名不符合标准"时提示"该标准 2024 年后未修订"→ 触发标准修订流程而非只当校验工具
- **整改 SLA 升级**：工单超时自动升级（3 天→部门负责人，7 天→治理委员会），工单不会在 demo 里静默堆积

## 四、Demo 设计

### 4.1 场景脚本（主线：责任人带着证据裁决）

**开场**：治理驾驶舱（质量分、重复率、待办、Agent 活动流实时滚动）。

**增量线（主故事）**——一批新物料申请（10 条/天）贯穿：

1. 提交：工厂提交批次，样例含命名不规范/单位错误/属性缺失/疑似重复
2. 标准校验：标准 Agent 只读校验，输出"符合/不符 + 修正建议 + 证据"，**建议不自动改**
3. 质量检核：质量 Agent 跑规则引擎，问题分级阻断/警告/提示，生成整改工单并指派责任人
4. 归并识别：归并 Agent 产出候选簇 + 证据链（字段差异/标准比对/历史编码/语义相似度来源），**推荐但不合并**
5. **Copilot 裁决工作台（核心演示点）**：业务 Owner 处理待办——建议卡片含证据链、冲突提示（如"语义相似但强度等级不同，不建议合并"）、风险标注、替代选项；**高风险操作要求输入审批意见或二次确认**；批准/驳回/改判全部留痕
6. **权责冲突插曲（v3 新增）**：一条归并建议跨两个事业部——A 同意 B 反对，演示升级审批链与会签留痕
7. 收尾：批准→金标入库→BTP 分发（复用现有）→驾驶舱指标实时变化

**存量线（并行副线）**：后台存量清洗——Agent 批量扫描存量库，产出归并工单+整改工单，每张工单带 Owner 指派与 SLA，汇入同一 Copilot 待办。

**现场验证环节（v3 新增，回应批评3）**：演示收尾，用客户自带的 5-10 条真实数据现场跑一遍流程。可能不完美——**这正是要展示的**：系统对未知数据的真实表现 + 未知缺陷如何被"人工裁决/工单闭环"承接。口径："demo 用受控样例演示工作流，真实效果以客户数据 PoC 为准。"

### 4.2 信任分级：证据类型分级（v3 核心修订，替代置信度）

**废弃**：LLM 置信度分数（logprobs/自评）——校准差，完全错误时同样给出 95%，不能作为任何分级的依据。

**启用：证据类型分级 L1/L2/L3**——信任建立在可验证的证据上：

| 级 | 证据来源 | 含义 | 系统行为 |
|----|----------|------|----------|
| L1 | 规则确定性命中（正则/映射表/字典） | "GB/T 5783" 命中标准字典；"8.8" 命中强度等级值域 | 建议采纳度最高；仍不自动写库，但裁决时可一键采纳 |
| L2 | 数据统计推断（同分类物料众数/分布/历史记录） | 属性缺失时"同分类 93% 物料材质为 45 钢" | 建议值带依据样本（展示来源记录），责任人确认 |
| L3 | 语义推断（LLM 相似度/语义判断） | "六角螺栓 镀锌" ≈ "六角头螺栓 电镀锌"（变体召回） | **只做候选推荐与冲突提示，永远标注"需人工确认"**；语义相似但标准/强度不同的 case 主动给出"不建议合并"警告 |

**防"无脑点确认"设计（回应批评2 深层）**：
- 裁决卡片强制三件套：证据链 + 风险标注 + 替代选项，缺一不可
- 高风险操作（归并执行、单位换算、属性修正）需输入审批意见或二次确认，不是纯点按钮
- 审计记录"批准人看到的证据快照"（当时展示了什么），事后争议可复盘"当时为什么批准"

### 4.3 数据设计（三类数据并存，回应批评3）

**领域选型**：紧固件 + 轴承两类典型工业物料——分类树 3 级、属性模板真实（规格、材质、强度等级、表面处理）。

**A 类：AI 能正确发现的（标准缺陷样例，演示工作流）**
- 金标存量 10,000 条（程序化生成）：重复簇 8-10 组（同名异码/单位变体/描述近似）、残缺记录 2-3%
- 增量批次：命名不规范 2-3、单位错误 2、属性缺失 2、疑似重复 3

**B 类：AI 会犯错的（v3 新增，演示系统兜底）**
| 样例 | AI 的失败模式 | 系统的兜底 |
|------|---------------|-----------|
| 强度 10.9 与 8.8 的同规格螺栓 | LLM 语义相似度高 → 倾向建议合并 | 规则层 L1 检测强度等级冲突 → **覆盖 LLM 建议**，明确"不建议合并" |
| 换算系数易混（"个"↔"包" 系数 12 vs 24） | LLM 可能自信给出错误系数 | 换算系数走 L1 映射表，冲突（多系统口径不一致）转人工协商工单 |
| 语义变体误判（"镀锌" vs "电镀锌" 不同工艺） | LLM 可能建议标准化改写 | 改写只给提示，不自动执行；涉及工艺差异的由 Owner 裁决 |
| 简繁/全半角混写 | 规则层即可处理 | L1 命中，提示级 |

**C 类：无法预定义的（历史数据乱象，演示闭环承接）**
- 编码段错位、分类挂载错误、属性串栏、OCR 录入错误——**不预埋、不假装能识别**；现场验证环节用客户真实数据自然触发，走"人工裁决 + 工单闭环 + 规则持续补充"。

> demo 成功标准（v3 重定义）：**不是"发现率 100%"，而是"每个缺陷都被闭环处理"**——自动建议、人工裁决或工单跟踪，无一静默漏过。

### 4.4 编排与可靠性（纪律约束 + 再评估决策点）

**自研轻量编排的成立条件（诚实边界）**：demo 规模（单机、单租户、10 条/天、可 mock 的 LLM）。以下机制进入 demo 骨架：

| 机制 | 设计 |
|------|------|
| 工单状态机 | `draft→pending→approved/rejected→executing→done/failed`，failed 可恢复 |
| 幂等键 | 每张工单/归并操作带 `request_id`，重试去重 |
| 补偿/回滚 | 归并执行前预检（金标冲突、分发在途）；执行失败置 `failed` 通知人工，**不做自动回滚（回滚本身是决策）** |
| 并发控制 | 金标记录 `version` 乐观锁；增量线与存量线操作串行化 |
| LLM 网关 | 超时 15s、重试 2 次、熔断降级 mock、token 成本上限告警 |
| trace 传播 | 全局 `trace_id` 贯穿全链；`agent_trace` 记录模型版本、输入摘要、证据引用、裁决快照 |

**编排纪律（v3 新增，回应批评4"风格不一致"）**：
- 所有 Agent 继承统一基类（错误处理、重试策略、trace 上报、日志格式），禁止各自为政
- 失败模式清单前置：超时 / 幂等冲突 / 部分失败 / 上下文超限 / LLM 不可用，逐项有对应策略，写进实现检查单

**框架再评估决策点（v3 新增）**：demo 验收后、产品化启动前，对照检查清单决定继续自研还是迁移 LangGraph 等框架：
- 状态恢复与检查点（进程崩溃后工单/归并状态是否可恢复）
- 人机协作断点（人工介入时 Agent 会话状态保持）
- 分布式 trace 与异步任务关联
- 多租户/多 Agent 并发规模
- 结论记录为正式决策，不留"demo 能用就继续"的隐性技术债

### 4.5 RalphLoop 技术改动点

**后端新增**（不动现有表结构语义，只加新表新包）：
- `app/skills/`：六个 Skill（naming/attribute/unit/quality_rule/duplicate_match/merge_executor），纯函数式接口（输入+标准 → 结论+建议+证据+证据级别 L1/L2/L3），可独立单测
- `app/agents/`：Standard/Quality/DedupAgent + Orchestrator，统一基类与纪律（4.4）
- `app/core/llm_gateway.py`：模型网关（mock/真实切换、超时/熔断/降级、token 成本、trace）
- 新表：`quality_ticket`、`merge_ticket`、`key_mapping`、`agent_trace`、`governance_owner`、`approval_evidence`（裁决证据快照，接问责链）

**API 新增**：`/api/copilot/*`（待办、批准/驳回/改判/审批意见/二次确认、问责查询）、`/api/governance/*`（质量报告、重复簇、归并执行——执行端点校验"已批准"状态）、`/api/owners/*`（责任人指派）、`/api/evidence/*`（证据链查询）

**前端新增**：Copilot 裁决工作台（三件套卡片：证据链+风险标注+替代选项；高风险二次确认；审批链与升级路径）、治理驾驶舱（recharts）、Agent 活动流（trace 时间线）、权责冲突视图（争议工单/会签）

**复用不动**：audit_service、审批流骨架、金标数据、BTP 分发、duplicate_detector（升级为规则通道）

## 五、售前叙事要点

1. **不叫 AI-native，叫 AI 增强**："确定性规则保证正确底线，AI 提升人的决策效率。主数据零容错，我们不做 AI 自动写库。"
2. **直面"谁拍板"**：demo 自带答案——裁决卡片显示 Owner、审批链、升级路径、问责留痕；跨事业部争议现场演示
3. **诚实声明边界**："demo 用受控样例演示工作流，真实效果以客户数据 PoC 为准"——预期管理即信任建设
4. **对比卖点（回应批评1）**：不是"AI 比规则强"，而是"AI 让治理责任人从 3 天决策缩短到 30 分钟，且每个决定有据可查"；信任分级 L1/L2/L3 可现场演示"系统为什么敢/不敢建议"
5. **AI 会犯错也讲**：B 类样例（10.9 vs 8.8）演示系统拦截 LLM 错误建议——"AI 也会错，我们的价值是让错误可见、可拦、可追"
